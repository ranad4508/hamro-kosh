# Hamro Kosh

Transparent community fund, expense, and lending management application —
a mobile app for a group of members who contribute money regularly into a
shared fund, borrow from it under configurable interest/repayment rules,
and see exactly where every rupee came from and went.

Built with **Flutter** (Android + iOS), **Firebase** (Auth, Firestore,
Storage, Messaging), a small **Cloud Functions** backend, **Cloudinary**
(image hosting), **Resend** (transactional email), and **Riverpod** +
**go_router**, following a feature-first, separation-of-concerns
architecture.

See [SRS.md](SRS.md) for the full software requirements specification.

### A security note on Cloudinary/Resend

Both are third-party services whose secret keys must never ship inside a
mobile app — any string embedded in a Flutter client can be pulled out of
the compiled APK/IPA by decompiling it. So:

- **Cloudinary**: the Flutter app uploads through an *unsigned* upload
  preset (`lib/core/services/cloudinary_service.dart`) — only the cloud
  name (a public identifier, not a secret) is in the client. Create the
  preset once in the Cloudinary console: Settings → Upload → Add upload
  preset → name it `hamro_kosh_unsigned` → Signing Mode: **Unsigned**.
- **Resend**: the API key lives only in `functions/index.js`, injected at
  deploy time from Firebase Secret Manager — see "Deploy the Cloud
  Function" below.

## Getting started

```bash
flutter pub get
flutter run
```

`lib/firebase_options.dart` already points at a real project (`hamro-kosh1`)
— Auth, Firestore, and Storage work out of the box. Two things still need a
one-time setup step from you before everything works end-to-end: creating
the Cloudinary upload preset (above) and deploying the Cloud Function
(below). Until then, `bootstrap.dart`'s Firebase init failure handling and
`authStateProvider`'s timeout fallback mean the app still launches and is
fully explorable even if something's misconfigured — it just falls back to
"signed out."

## Firebase project (already connected)

`hamro-kosh1` is wired up via `flutterfire configure` — Android's native
config (`android/app/google-services.json`, the Gradle plugin) is in place.
**iOS still needs `ios/Runner/GoogleService-Info.plist`**: `flutterfire
configure` couldn't place it from this Windows machine; re-run the wizard
(`flutterfire configure`, select iOS) from a Mac, or add the file manually
from the Firebase console → Project settings → your iOS app.

Firestore security rules (`firestore.rules`) are written and deployed —
`firebase deploy --only firestore:rules` after any further edits to that
file.

### Deploy the Cloud Function

`functions/index.js` (`createUserAccount`) is the only thing allowed to
call Resend, and it needs the **Blaze (pay-as-you-go)** plan — any Cloud
Function with outbound network access to a non-Google API requires it,
regardless of which email provider is behind that call. The free tier is
generous; this app won't approach paid usage. Upgrade at
https://console.firebase.google.com/project/hamro-kosh1/usage/details,
then:

```bash
firebase functions:secrets:set RESEND_API_KEY
# paste the Resend API key when prompted — it's stored in Secret Manager,
# never written to a file in this repo

cd functions && npm install && cd ..
firebase deploy --only functions
```

If you'd rather not put this project on Blaze, the alternative is hosting
this one function elsewhere (Cloudflare Workers' free tier, for example)
and having the Flutter app call that HTTPS endpoint instead — ask if you
want that swapped in; the client-side call in
`admin_create_user_screen.dart` would just point at a different URL.

### RBAC & the super admin

Three roles: `member` (self-registers, awaits approval), `admin` (approves
members, manages the fund, can create member accounts), and `superAdmin`
(also creates admin accounts; can't be deleted or demoted through any
client write; never shown in any member/admin list — see
`firestore.rules` and `MembersRepository._excludingSuperAdmin`).

The super admin (`ranad4508@gmail.com`) is seeded automatically,
server-side, by `seedSuperAdminIfMissing()` in `functions/index.js` — it
runs once per cold start of the Functions instance, checks Firestore for
an existing `role == "superAdmin"` first, and does nothing if one's
already there, so redeploys are always safe no-ops. This intentionally
is **not** something the Flutter client can trigger: a mobile client can
never be trusted to create a Firebase Auth user for someone else or write
an elevated role past `firestore.rules`, and "whoever calls an endpoint
first becomes super admin" would be a race anyone could win. It goes live
the same moment you deploy functions (below) — change its password from
Profile → Change password after first sign-in. Every other admin/member
account goes through **Manage Members → Create account** in the app,
which emails the new user their login credentials.

### Transparency emails

`notifyOnTransaction` (a Firestore trigger on `transactions/{id}`) emails
every approved, active member whenever a monthly/special contribution or a
loan disbursement is recorded — SRS §12/§41/§54's transparency principle
extended to email, not just in-app. Both this and the welcome email above
render through one shared branded HTML template
(`buildEmailShell` in `functions/index.js`): a header, a greeting, a lede,
the main content block, and a closing note.
